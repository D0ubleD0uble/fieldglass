# Changelog

All notable changes to Fieldglass are documented here. The format roughly follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Versioning is plain [Semantic Versioning](https://semver.org/spec/v2.0.0.html), and every release is a stable one. Pre-1.0, a minor bump (`0.3.0` → `0.4.0`) may break the Rust API; a patch (`0.3.0` → `0.3.1`) does not. The same version numbers the extension and the library crates.

## [Unreleased]

### Added

- **Fieldglass runs in a browser.** Two new crates. `fieldglass` is the host-neutral API the project has been heading toward since [ADR-0006](docs/decisions/0006-hosts-are-bindings-over-a-plain-data-api.md): open bytes, list messages, decode a field, and get back contiguous values, a separate presence mask, and enough georeferencing to place the raster on a map — a PROJ string and an origin-and-spacing affine. `fieldglass-wasm` is a binding of it for `wasm32-unknown-unknown`, meant to run in a Web Worker, and it is only the buffer handoff and the error mapping; everything it does is decided upstream. GRIB1 and GRIB2, and the four grid families NOAA and ECMWF publish on. Nothing in the VS Code extension changes. Closes #460.

- **Colour is decided once, in Rust, and a GPU can consume the decision.** A browser map colours on the graphics card so that changing the colormap never re-decodes the file, which normally means writing the colour rule a second time in a shader and watching the two drift apart. Instead the painter's own 256-entry table leaves Rust as data and the package ships the shader that reads it, so the CPU painter is the reference the GPU is checked against rather than its rival. The field is rebased in double precision before it reaches the shader, which is not a detail: a shader that does that subtraction itself in single precision loses the range rather than the last digit, and for a tight display range over large values — geopotential, pressure in pascals — it can be wrong by half the colour table. Over the committed fixtures the two paths pick the same table entry for all 6,292,128 cells tested, and a WebGL read-back of a real field in a browser matched the CPU picture pixel for pixel.

- **The value type follows the file.** A decoded field comes back as 32-bit floats only when every value in it survives that narrowing exactly, and as 64-bit otherwise. The usual shortcut — "the packing used 24 bits or fewer, so it fits" — is not true once the reference value sits far from zero or the file uses a decimal scale factor, and it silently costs digits on ordinary NCEP output. A caller that wants 32-bit for a graphics texture regardless asks for it by name and gets the conversion it chose.

- **A GRIB1 grid answers its own questions.** Four pieces of grid policy were written out by hand in the VS Code binding rather than by the parser that owns them: which way the grid scans, the sign of `Dx`/`Dy` (GRIB1 stores magnitudes and puts the direction in a flag byte), the ±60° true-scale parallel a polar stereographic grid never states, and whether a message has a raster at all. Each is now an accessor on the grid description, so a second consumer of the crate gets the same answer instead of writing a fifth version of the rule — one of the hand-written ones already disagreed with the others about Lambert and polar stereographic grids. A message also reports which decode method applies to it, which is not something a caller can work out from the packing label: a `grid_simple_matrix` message may or may not carry a matrix, and only its sub-header says which.

- **A parsed grid description converts to one typed value.** GRIB1 and GRIB2 grids now convert directly into `GridGeometry`, the type `fieldglass-core` gained for placing a field on the Earth, so a consumer no longer re-derives the per-family dispatch from a flat bag of optional fields. A family that is not modelled yet reports itself by name rather than failing, so a message can say which grid was declined.

### Fixed

- **A global grid's default map window covers the seam.** Reprojecting a whole-world field onto its own extent stopped at the last column the file declares rather than going the full way round, leaving the antimeridian as a one-cell stripe of background. The gap between the last column and the first belongs to the grid, and is now filled.

- **Boustrophedon grids come out in the right order for library users too.** Some products, the National Blend of Models among them, store their rows in alternating directions: the first runs west to east, the next east to west. Fieldglass has flipped those rows back since 0.2.0, but it did so in the layer the VS Code extension talks to, not in the `fieldglass-grib2` crate — so anyone decoding a GRIB2 file with the crate directly got every second row reversed, with nothing in the result to say so. The flip now happens inside `decode_message_values`, alongside the packing-level row undo that already lived there. Every point of a real 2345 × 1597 NBM field now matches what eccodes' own geolocating decode reports. What the extension shows is unchanged. A grid that alternates its rows *and* stores columns rather than rows is a layout the flip cannot be applied to; it is now refused with an explanation instead of returning a quietly scrambled field.

## [0.5.0] — 2026-09-04

### Added

- **A plain HDF5 file's variables can be drawn.** An `.h5` written straight through HDF5 rather than by the netCDF-4 API declares no dimensions, and Fieldglass invented names for those axes without ever giving them a length — so such a file opened, listed its variables, and then reported every one as having no extent. Nothing could be rendered. The axes are now sized from each dataset's own dataspace, following the same rule netCDF-C uses, so Fieldglass and `ncdump -h` name the same axis `phony_dim_0`. That rule is fussier than it looks: two axes of equal length still get two separate dimensions, a second dataset of the same shape reuses the first's pair, and a transposed shape reuses that pair the other way round. Such a file has no coordinate variables, so there is still no geolocation and no map — it behaves like WRF output does today, where you pick the image axes yourself and read the grid in its source projection. Files written by the netCDF-4 API are untouched, since they declare their dimensions properly and never take this path.

- **NetCDF units read the way GRIB units do, and now appear at all.** The units column typesets GRIB's notation — `m s⁻¹` rather than `m/s` — and NetCDF was the one format left showing its own raw. It turned out to be showing rather less than that: the render panel's title line and point-probe readout carried no units for a NetCDF file, because the panel built its own metadata and had nowhere to read them from. Both are fixed. The rule is deliberately narrow, and written down in [ADR-0007](docs/decisions/0007-netcdf-unit-notation.md): notation is typeset, names are left exactly as the file's author wrote them. `m/s` becomes `m s⁻¹` and `um` becomes `µm` — restoring a character the ASCII attribute could not hold, the same act as turning `-1` into a superscript — while `meters` stays `meters` and `kelvin` stays `kelvin`, because which word to use is the author's choice and not a viewer's business. Three units the tables were missing are recognised for every format: the micrometre, the hour as `hr`, and the decibar. That last group is what the change is really worth — GOES ABI radiance, written `W m-2 sr-1 um-1`, was passing through untouched because one symbol was unknown, and it now reads `W m⁻² sr⁻¹ µm⁻¹`. Closes #453.

- **NetCDF renders face north-up, like everything else.** A GRIB message says which way its rows run, and the source view is flipped so north is at the top. NetCDF files say no such thing, and nothing had been put in its place — so a file whose latitude increases with the row index, which is the ordinary convention and what most files use, drew upside-down. Sea-surface temperature and ocean model output were both affected. The latitude axis now answers the question the GRIB flag answers, and for grids that give a position per cell rather than an axis, the first and last rows are compared directly. Reprojected views were never affected, only the raw grid view. Files that already read the right way up, including GOES imagery and WRF output, are untouched.

- **A curvilinear file opens on one of its own fields.** The latitude and longitude arrays that place such a grid were offered in the variable picker alongside the real fields, and sorted first — so an ocean file opened on a picture of its own latitude rather than on the ice. They are coordinates, not fields, and the picker no longer lists them. The one-dimensional equivalent was already excluded; a two-dimensional coordinate is not named after a dimension, so the existing rule never caught it.

- **A curvilinear file opens on the right plane.** The grids above render, but the slice picker had nothing to pre-select their image axes from — a curvilinear variable has no one-dimensional latitude or longitude to detect — so it fell back to the variable's first two dimensions. For a satellite swath that happens to be right. For an ocean field shaped time × Y × X it is not: opening one gave a single-pixel-tall sliver of the wrong plane, ungeolocated, and you had to work out which dimensions were the map and set them by hand. The two-dimensional coordinate arrays already say which they are, so the picker reads the answer from them. Files with ordinary latitude and longitude axes are unaffected. Closes #218.

- **Curvilinear NetCDF grids render on a map.** Ocean models and satellite instruments often describe where their data is by giving a latitude and longitude for every single cell, rather than by a projection you can compute positions from. Fieldglass could open those files and show the numbers as a flat image, but not put them on a map — reprojection reported the grid as having no coordinates, and so did contours and the `lat,lon,value` CSV export. Now the cell positions are the geometry: pick any projection, probe a point, draw contours, export coordinates. The two shapes this covers are ocean model output on a tripolar mesh, where the grid folds over the Arctic so that a single row of the array runs up over the pole and back down, and satellite swaths, where every pixel is geolocated individually and a pass can cross the antimeridian and sweep over a pole. Both are in the test corpus, and every cell of both is checked to land where its own file says it does. Because such a grid answers with a cell rather than a position inside one — and neighbouring cells in the array can be on opposite sides of the fold — smooth (bilinear) resampling is quietly turned down to nearest rather than blending two places that are nowhere near each other. Closes #445.

- **Two curvilinear NetCDF files join the test corpus.** Ocean model output and satellite swath products describe their geometry as a list rather than a formula: a latitude and a longitude for every single cell, with no projection to recover one from. Fieldglass opens such files today but cannot put them on a map, and there was no example of one to work against. There are now two, both NOAA public-domain: a window of the RTOFS global ocean model centred on the pole its grid folds around, and a window of a NOAA-21 MiRS satellite pass crossing the antimeridian at 85° south. Neither is a comfortable example — the awkward parts are the point, since a convenient window would let a wrong implementation look right. Nothing changes in what Fieldglass shows yet; this is the groundwork for putting these grids on a map. Closes #444.

- **Reduced Gaussian grids in GRIB2 decode and render.** This is what ECMWF publishes on: each row of latitude holds a different number of points, so the file states no `Ni` at all, and Fieldglass would open such a message, name its grid `N32`, and then refuse to show a single value — "reduced grids are not yet supported for decode". They now decode, render, reproject, probe, contour and export like any other grid, the way GRIB1 has since 0.2.0. Each row is widened to the width of the widest one at the point the field is decoded, so everything downstream sees an ordinary rectangle; the widening maps each output column to the nearest point by longitude and wraps at the antimeridian, rather than stretching a narrow polar row of 20 points across the whole width. The size column still shows the grid's name, `N32` or `O32`, because that is what the file says and what every other tool prints. Both committed fixtures now decode to the values eccodes decodes, point for point. Closes #503.

- **GRIB2 HEALPix grids (§3.150) render.** HEALPix tiles the sphere into `12·Nside²` equal-area pixels and is what ECMWF publishes its higher-resolution open data on; Fieldglass used to show those files as `unsupported(3.150)`. The section now decodes — `Nside`, the ordering, and the pixel count — and the values come back in pixel order. Both orderings are handled: RING, which walks each ring of constant latitude in turn, and NESTED, which is a quadtree per face and is converted through the same position maps rather than a second implementation. Pixel centres are checked against eccodes for every pixel of two resolutions in both orderings, not a sample. Unlike every other grid this is a list of pixels rather than rows and columns, so it has no `(ni, nj)` for a renderer to work from; it is resampled onto a regular lat/lon grid at decode, the way spectral fields already are, so reprojection, the point probe, contours and CSV export all work with no special case. The grid is chosen to match the HEALPix pixel size — `58.63/Nside` degrees — so no pixel is skipped, and capped at the same 0.5° the spectral path pins, past which the memory is real and a viewer cannot show the difference. Closes #442 and #443.

- **Contours and long-format CSV work on projected grids.** Lambert conformal, polar stereographic, transverse Mercator and Lambert azimuthal equal-area grids — HRRR, NAM, RAP, NBM, UKV and EFAS among them — refused both: the isoline overlay reported "contours not yet supported for grid type", and a `lat,lon,value` export said the grid gave no per-point coordinates. Neither had been true since those projections learned to report the position of any grid point; only the dispatch had not caught up. Both now geolocate through the same forward map the image is reprojected with, checked grid point by grid point against eccodes. WRF files read through NetCDF get the same, since their `MAP_PROJ` puts them on those projections. The list of supported grids the two refusal messages read out is now the list that decides what is refused, so they cannot drift apart again. Clicking one of those fields in its own projection reports where the point is as well as what it reads, which it could not before either. Closes #470.

- **Lambert azimuthal equal-area grids (GRIB2 §3.140) decode and render.** This is the projection behind the ETRS89-LAEA European statistical grid — the CEMS/EFAS flood-forecasting archive is published on it, as are EUMETSAT OSI SAF sea-ice products — and Fieldglass used to show those files as `unsupported(3.140)`. Like transverse Mercator, it runs on the spheroid the message declares rather than its mean radius: eccodes does the same, and the approximation would be about 13.5 km out over the European domain. Grids tangent at the south pole work, which is more than can currently be said for eccodes: its own iterator refuses them.

- **Transverse Mercator grids (GRIB2 §3.12) decode and render.** This is the projection the Met Office publishes UKV on, its 1.5 km UK model, and Fieldglass used to show those files as `unsupported(3.12)` — metadata only, with no way to put the field on a map. They now parse and reproject like any other grid. Unlike the other projected templates, this one runs on the spheroid the message declares rather than its mean radius: UKV declares Airy 1830, and the spherical approximation would place the field about 2.8 km from where it belongs. The projection is checked against PROJ, because eccodes has no transverse-Mercator geolocation to check against at any version. Closes #422.

- **NCEP GRIB2 files name their own local parameters.** GFS, HRRR, NAM, RAP and NBM all use local parameter codes for the fields NCEP adds to the WMO set, and those showed as `Parameter 0/3/192` with no name or units — on the most widely redistributed GRIB2 data there is. Fieldglass now ships NCEP's table: 479 parameters with the uppercase abbreviations NCEP itself publishes (`MSLET`, `REFC`, `CSNOW`), generated from a pinned wgrib2 release, which is the only machine-readable form of NCO's parameter documentation. eccodes ships a smaller version of the same table, and the two were compared entry by entry: they agree on all but three of the 313 they share, and wgrib2 covers 166 more. NCEP writes its units with a caret (`kg/m^2/s`), which the units column now reads and typesets like every other notation. Closes #426.

- **DWD/ICON GRIB2 files name their own local parameters.** ICON output uses local parameter codes for its tendencies, sub-grid diagnostics and a handful of surface fields, which the WMO master tables do not define, so those messages showed as `Parameter 0/1/203` with no name or units. Fieldglass now ships DWD's own table — 213 parameters with short names, generated from eccodes 2.34.1 — and resolves them for files from that centre only. Most of DWD's published table sits on standard codes that the WMO tables already name correctly, and Fieldglass leaves those alone; entries eccodes distinguishes using information the parameter lookup does not see are left out rather than guessed at, as are DWD's `DUMMY_n` placeholders. Every entry that does ship was checked against eccodes itself, and the result was confirmed on real ICON-D2 open-data files. Closes #425.

- **ECMWF GRIB2 files name their own parameters.** Codes above 191 are local: they mean whatever the originating centre says, and the WMO master tables do not define them, so a large share of any ECMWF file showed as `Parameter 192/128/4` with no name or units. Fieldglass now ships ECMWF's own table — 2,826 parameters with short names, generated from eccodes 2.34.1 — and resolves them for files from that centre only. Thirteen of them ECMWF defines only for a particular revision of its own table, and those resolve only for files declaring that revision. Entries eccodes distinguishes using information the parameter lookup does not see are deliberately left out rather than guessed at, so the table is silent in exactly the places eccodes is; every entry that does ship was checked against eccodes itself. Closes #424.

- **NetCDF-4 files compressed with zstd now open.** zstd (HDF5 filter id 32015) arrived in netcdf-c 4.9 and is the compressor DKRZ recommends for new climate archives, so it turns up in recent output; its presence used to fail the whole file. It is now decoded in pure Rust, composing with shuffle and fletcher32 in any order. This also goes beyond a default netcdf-c install, which frequently has no working zstd plugin at runtime. Closes #413.
- **Formal verification of the decode kernel is wired up.** The small arithmetic kernel that turns untrusted bytes into numbers — bit reading, scaling, spatial differencing, group expansion — is where a malformed file causes wrong values or a panic, and every GRIB value passes through it. [Verus](https://github.com/verus-lang/verus) now runs against it via `scripts/verify.sh`, with a first proof in place. Nothing that ships depends on Verus: the proofs live in a crate outside the workspace, and CI asserts that no Verus crate reaches the shipped dependency graph, so the six release targets are untouched. See [`docs/verification.md`](docs/verification.md). Closes #197.
- **GRIB2 units read consistently.** Bringing in the WMO master tables left the units column mixing two notations: the curated parameters showed `m s⁻¹` while the 1,387 generated ones showed WMO's own `m/s` and `kg m-2`, sometimes for the same quantity. They are now typeset uniformly at display time, so the generated table stays byte-identical to its pinned upstream. Strings that are not units — cross-references like `Code table 4.253`, the `CCITT IA5` encoding, `Numeric`, and the space-weather fluxes written as `(m2 s sr eV/nuc)-1` — are shown exactly as the WMO publishes them. Closes #432.

- **GRIB2 parameters show the short name a forecaster scans for.** WMO publishes names and units for its master parameter table but no abbreviations, so of the 1,387 parameters Fieldglass ships, 1,346 showed a blank in that column — full for the local parameters, empty for 97% of the standard ones, which is backwards from what a reader expects. The column is now filled from the abbreviations NCEP publishes alongside the same WMO triples (`TMP`, `UGRD`, `APCP`, `HTSGW`), taken from the pinned wgrib2 release Fieldglass already reads the NCEP local table from. 1,220 of the 1,387 now carry one; the 167 that do not show name and units as before. Most are triples that table does not cover, mainly in the health and socioeconomic discipline WMO added later. Ten are parameters NCO itself publishes no abbreviation for, where wgrib2 writes a placeholder (`var2s31`) to fill its own table; those stay blank, because a made-up label reads as more certain than no label. The two tables are joined on the parameter triple, and every row was checked to name a parameter WMO actually defines, so a short name can never invent a field. Two of the 41 hand-written abbreviations turned out to disagree with what NCO publishes, and both were wrong in the same way three parameters were found to be earlier: a GRIB1 code carried onto a GRIB2 triple. `0/1/22` read `CLWMR`, the GRIB1 name for cloud mixing ratio, where GRIB2 has `CLMR`; `10/0/3` read `WVHGT`, which in GRIB2 is significant height of *wind waves*, a different parameter — so that entry paired one parameter's abbreviation with another's name. Both are corrected, and the hand-written abbreviations are now checked against the published table on every test run, so one cannot drift again. One knock-on: the field picker labels a message by its abbreviation and falls back to the full name, so the 1,189 fields that had no abbreviation now read `#3 · ALBDO · surface` where they read `#3 · Albedo · surface` before — which is what that label was always meant to show. Closes #469.

- **GRIB2 fields are named from the full WMO master parameter tables.** Fieldglass carried 44 curated parameters, so most fields in a real ECMWF or NCEP file displayed as `Parameter 0/20/5` with no units. It now ships the complete WMO Code Table 4.2 — 1,387 parameters across all 60 discipline/category tables — generated from a pinned `wmo-im/GRIB2` release, along with Code Table 4.5 (fixed surface types) and 4.4 (time-range units). Deprecated entries are kept, since files in the wild still use them. WMO publishes no short names of its own; where those come from is described in the next entry. Closes #415.

- **NetCDF-4 files carrying a fletcher32 checksum now open.** fletcher32 (HDF5 filter id 3) is a checksum rather than a compressor, but its presence in a pipeline used to fail the whole file — including files whose actual compression was deflate, which Fieldglass already decoded. It is now read: the four checksum bytes each chunk carries are verified and stripped, and a chunk whose bytes have been altered is reported as corrupt rather than decoded into plausible-looking numbers. Composes with deflate and shuffle in any order. Closes #412.

### Fixed

- **A coarse grid no longer reprojects to a postage stamp.** A reprojected raster took its size from the source grid, which holds a real forecast grid at its own resolution but left nothing underneath it. A HEALPix `Nside 4` field resamples to 26 by 14 at its own pixel scale, so it drew a 26 by 26 orthographic globe: the data's edge was a staircase while the coastline overlay was a smooth curve on the projection's true limb, which reads as missing data around the rim, and the exported PNG came out 26 pixels wide. Reprojections are now drawn at 0.5°, the resolution spectral and HEALPix fields are already synthesized at, whenever the source is coarser than that. The limb, the seam and the map body then resolve at display scale and the overlays register against them. Upsampling adds nothing to the field itself, so the source view is deliberately left alone: there a blocky picture is the honest one. Grids already at or above that resolution are untouched, which covers the large ones: GFS and ECMWF at 1440 across, HRRR at 1799, MRMS at 7000. The smaller operational domains do move, and are meant to — NAM's CONUS grid is 614 across and RAP's is 451, so both are now drawn at 720 rather than at their own resolution. Closes #514.

- **A satellite swath is no longer drawn many times too tall.** Reprojecting took the output raster's shape from the source array, which is right for a grid whose array *is* its geography — a GFS field is rows of latitude by columns of longitude, and copying that shape reproduces it exactly. A curvilinear grid has no such correspondence: a satellite swath is stored scan line by field of view, which says nothing about where the pass went. A NOAA-21 half orbit is 96 by 768 for a window spanning 355° of longitude and 117° of latitude, so it was drawn into a frame more than twenty times too tall to be read. Such a grid now takes its shape from the window and its pixel budget from the source, the same rule the whole-world projections already used. Grids whose axes are latitude and longitude are untouched, because for them the old answer was already the best one. Closes #515.

- **A global grid no longer draws its first column twice, or sits a fraction of a cell east of where it belongs.** Reprojecting to equirectangular or Web Mercator spread the output columns from the first meridian to the last inclusive — the right convention for latitude, where you want a row on each pole, but wrong for longitude, where 0° and 360° are the same meridian. The last column therefore re-drew the first, and every column in between sat `n / (n - 1)` too far east: a quarter of a degree at the eastern edge of a 1440-column GFS field, and nearly 14° on a HEALPix field resampled to 26 columns, where the coastline overlay visibly stopped a whole column short of the picture. A full-turn window now tiles the circle exactly once. Grids that declare a duplicated seam column of their own are unaffected, since their window is an interval rather than a circle. A side effect worth having: a global grid's own spacing now falls out exactly — 0.25° for GFS, 0.5° for a synthesized spectral field — so an equirectangular render of one is a straight copy rather than a resample.

- **A NetCDF dimension with one slice no longer reads as empty.** The slice steppers labelled themselves with the highest index you could type, after a slash — so a 22-channel dimension read `0/21`, and a dimension holding a single time step read `0/0`, which looks like zero of zero rather than the one slice it has. The index itself stays 0-based, matching the probe readout, the CSV export and every NetCDF tool; the hint beside it now states the range you may type (`0–21`), and a dimension with nothing to step says `only slice` and disables a slider that could never move.

- **The render panel re-labels itself when you switch NetCDF variables.** A NetCDF file is browsed inside one panel: the variable picker changes what is drawn without opening a new view. The heading and the point-probe units, though, were fixed at the variable the panel opened on, so moving the picker left the old label in place — in a sea-surface file, `Celsius` reported against sea-ice concentration, which is a percentage. A wrong unit beside a real number is worse than none, and the export carried it into the PNG title too. The label now travels with each render, composed by the same code that builds the heading the panel opens with, so the two cannot drift apart.

- **A NetCDF variable's units are visible without rendering it.** The metadata view lists each variable's attributes, but previews only the first three and hides the rest behind "+N more" — and `units` is routinely past that cut, fifth on every field of a NOAA OISST file. A reader looking at the variables table saw no units at all, and the only way to find them was to render the variable and read the panel title. The table has a Units column now, filled by the same typesetting the render panel uses, so both places print the same string.

- **Turning off the last map overlay no longer erases the contours.** Contours and the geographic layers — coastlines, borders, lakes, rivers, graticule — share one canvas. Switching off the last of those layers wiped the whole canvas and repainted nothing, so contours vanished even though their own box was still ticked; they returned only when something else forced a redraw, such as resizing the panel. The clear now repaints whatever is still enabled. An overlay that fails to project no longer takes the contours down with it either.

- **A projected grid's far corner is read the way the file scans, and a degenerate one no longer reports "NaN".** Lambert conformal and polar stereographic grids store their spacings as unsigned magnitudes, and the scanning-mode flags say which way the grid runs from its first point — but the corner calculation walked east and north regardless. On a north-to-south grid that put the reported far corner on the wrong side of the grid's own origin, tens of degrees away on a different meridian, and disagreeing with the reprojection, which had always applied the sign. Every committed fixture scans the same way, which is why nothing caught it. Separately, a cone too degenerate to invert (both standard parallels on the equator) produced `NaN`, and the message table showed the literal text "NaN"; such a grid now reports no corner pair at all, while still showing the first point, which the file states outright. Closes #472.

- **A wide message table scrolls instead of pushing the page sideways.** The message table sets every cell to a single line and has thirteen columns, four of them free text — parameter name, level type, bounds, and a centre name carrying WMO's own wording at up to 82 characters. A row wide enough to outrun the editor pane took the whole document with it: the heading and the render panel moved too, and the only way back was to widen the pane. The table now scrolls inside itself and the page around it stays put. The NetCDF dimensions, attributes and variables tables get the same treatment; their attribute column is easily as wide. The narrower fix from the previous release, which wrapped the centre column alone, is removed rather than kept alongside this one — a single wrapping column gave that row a different height from every other, which is what makes a dense table hard to read. Closes #452.

- **An octahedral grid is no longer drawn a fraction of a cell out of place.** ECMWF's newer octahedral grids (`O32`, `O1280`) write their last-point longitude from the older grid of the same Gaussian number, which is narrower than the octahedral grid's widest row — so placing the field on the longitudes the file declares squeezed 144 columns into a 128-column span, sliding everything east of Greenwich progressively westward. The render now derives the east edge from the row widths the file lists, which is where the data actually is; the message table still reports what the file states. Classic grids are unaffected, because for them the two are the same number.

- **Contours and CSV coordinates work on reduced grids.** A reduced GRIB1 grid rendered and reprojected but refused to draw isolines or export a `lat,lon,value` CSV, reporting the grid as one with no coordinates — while the image behind it was being placed with the very map that was said not to exist. Reduced grids arrive at every consumer already widened into a regular raster, so the coordinates were always available. Their contours also close across the antimeridian now, instead of leaving a one-column gap down the seam.

- **The same reduced grid reads the same way in both GRIB editions.** The message table's grid-type column showed `reduced_gaussian` for a GRIB1 file and `gaussian` for the GRIB2 form of the same grid, because GRIB2 gives the regular and reduced variants one template number. Both now say `reduced_gaussian`, which is the distinction eccodes draws too — it calls them `regular_gg` and `reduced_gg`.

- **A field with no rows and columns now reports its own size instead of a dash.** Spectral, bi-Fourier and HEALPix messages are not laid out on a grid, so the message table's size column had nothing to put in them and showed `—`. That reads as "the file does not say", when in fact each of these states its size precisely, in its own units: a spectral field by its truncation, a HEALPix field by `Nside`. The column now shows `T63`, `Nside 4`, or the bi-Fourier resolution pair, in both GRIB editions, and the render caption does the same. Grids that do have dimensions are unaffected — they report `Ni×Nj` exactly as before.

- **Reduced Gaussian grids are named the way every other tool names them.** ECMWF's ordinary output is a reduced Gaussian grid, where each row of latitude holds a different number of points. In GRIB2 that meant no `Ni` at all, so the size column showed `—`; in GRIB1 it showed `128×64`, which is the rectangle Fieldglass expands the rows into rather than anything the file contains — the grid in question holds 6,114 points, not 8,192. Both now report the grid's name, `N32`, and both agree. Grids of the newer octahedral kind are told apart from the classic ones and named `O32`, using the same rule eccodes uses — the row widths rise by exactly four to the equator and fall by four again — rather than an arithmetic shortcut that reads a single row. Regular Gaussian grids still report their dimensions, because for them that is the answer.


- **Geostationary sectors no longer lose a speckled border.** GOES ABI and Meteosat sectors dropped grid points along their first and last row and column: the inverse map refused them, and a refused point renders as a transparent pixel. All four planar projections already snapped an index that round-off had pushed a hair past a grid edge back onto it; geostationary was the one family never given that rule, and its scan angles come from a ray/ellipsoid intersection, which does not land on a window bound exactly. On the real ABI CONUS window, 414 of the 37,003 points that are on the Earth could not be placed. The result was not a clean missing border but a speckle, because whether a given edge cell survived depended on the arithmetic for that one point. Sub-sector products were worst hit, since every one of their points is on the Earth; on a full disc most of the outer ring looks past the limb and is legitimately absent anyway. Interior points were never affected, and a test now says so. The tolerance is one named value shared with the planar projectors, rather than two that can drift. Closes #490.

- **A polar stereographic grid that crosses the equator now renders all of it.** The inverse map refused every point in the hemisphere opposite the projection pole, so a north polar grid reaching south of the equator lost that part of the image to background — and the part it lost was real data the file contained. Environment Canada's regional 135x95 grid is one: its far corner sits at 4.7 degrees south, and 328 of its 12,825 points, one in forty, could not be placed. The guard was there to avoid a singularity, but the singularity is only at the opposite pole itself, which the grid extent already excludes; the projection is well defined and unambiguous everywhere else. Grids centred on the pole and wide enough to reach past the equator were affected the same way, as were southern grids reaching north. The check that would have caught it was already in the codebase, but it ran on small synthetic grids rather than the real ones — the polar case started at 27 degrees north, so it could never have found this. It now walks every grid point of every real fixture grid, in all nine grid layouts Fieldglass reads. Closes #488.

- **Lambert and polar stereographic grids report their real last grid point.** The message table's coordinate columns showed `LaD`/`LoV` for these grids — the projection's latitude of true scale and its orientation longitude — because the templates state no second corner and, when that code was written, there was nothing to ask for one. It read as a plausible pair of degrees in a column labelled "last point", and put a longitude of 265 where every other grid reports ±180. They now report the corner the grid actually ends at, derived from the projection exactly as transverse Mercator and Lambert azimuthal already did, and checked against eccodes' own point iterator. The projection parameters are still shown, under their own names. A GRIB1 grid that scans north to south had its far corner computed in the wrong direction; it now follows the grid's own scan, as the renderer always has.

- **A contour crossing the ±180° meridian no longer streaks across the map.** Where the antimeridian runs through a grid cell, its two corners are a few kilometres apart but read +179.9° and −179.9°, and a contour vertex interpolated between them landed near 0° — a line drawn from one edge of the map to the other. It affected rotated grids over the Pacific, and would have affected every projected grid there as soon as they started contouring.

- **Nine GRIB2 code-table entries named the wrong thing.** Six were in code tables whose codes the WMO has since assigned to something else: production status (Table 1.3) 10-13 read "Climate Data Record", "Climate projections", "Climate Forecast System Reanalysis" and "Reforecasts", where the WMO assigns 10-11 to Copernicus regional reanalysis and 12-13 to Destination Earth; statistical process (Table 4.10) 12 and 13 read "Confidence index" and "Quality indicator", where the WMO has "Return period" and "Median". A file using any of them was described with a label that has not been correct for several table revisions. All nine are now checked against the WMO tables on every test run, so the curated labels cannot drift from the standard again.

- **Three GRIB2 parameters were named as the wrong quantity.** Their curated entries carried GRIB1 ON388 parameter codes on GRIB2 discipline/category/number triples: `10/1/2` was labelled "Sea surface temperature" but is the u-component of current, `2/0/5` was labelled "Soil moisture content" but is water runoff, and `0/3/9` was labelled "Density" but is geopotential height anomaly. A file carrying any of the three displayed a confident, wrong name and the wrong units. All three now resolve from the WMO master table, and the quantities they were mistaken for resolve at their real triples — including sea-surface temperature, which is `10/3/0` "Water temperature" and had never resolved before. Found by cross-checking the generated tables against eccodes, which is now a test.

### Changed

- **Originating centres now come from the WMO Common Code Tables, and sub-centres are named.** The centre column was a hand-picked subset of 22 codes for GRIB2 and 53 for GRIB1; anything outside it displayed as a bare number, and nothing checked the names against the standard. Both tables are now generated from a pinned `wmo-im/CCT` release — 309 centres for GRIB2, 239 for GRIB1 — and checked against it on every test run. The two editions get separate tables because WMO publishes separate ones: they disagree on eleven names, GRIB2 defines 70 centres that a GRIB1 file cannot express, and code 255 means "missing" in one and "not to be used" in the other. Sixteen entries keep the operating agency's acronym or a diacritic that WMO's own text drops, so no centre reads less clearly than before. The sub-centre field, parsed since the beginning but never displayed, now shows alongside the centre — resolved from the centre and sub-centre together, because the same sub-centre code means different things under different centres. Closes #440.

- **GRIB1 units read consistently too.** The units column was typeset for GRIB2 but shown raw for GRIB1, whose tables carry two more ASCII notations: the ECMWF local tables are generated from eccodes, which writes exponents Fortran-style (`kg m**-2`), and WMO ON388 chains solidi (`kg/m2/s`). Both are now typeset at display time, so `kg m**-2`, `kg m-2` and `kg/m2` all read `kg m⁻²` whichever edition the file is. The generated tables are untouched and stay reproducible from their upstream. Strings that are not products of units — `m of water equivalent`, `(0 - 1)`, `log10(kg/m3)`, the one entry written `K*m/s` — are shown exactly as published. Closes #441.

- **A compressed NetCDF-4 chunk can no longer name its own allocation size.** Both decompressors now stop at 256 MiB per chunk. A compressed chunk is attacker-controlled and its expansion ratio is unbounded, so a few kilobytes on disk could previously ask for an arbitrarily large allocation; the ceiling is far past any real HDF5 chunk, whose default cache size in libhdf5 is 1 MiB.

- **Opening a GRIB1 file uses half the memory it did.** The handle kept its own copy of the whole file alongside the reader's, so a GRIB1 file cost two full copies on top of the buffer the editor already holds. It now keeps one: the single place that needed the original octets borrows them from the reader. On a 205 MB file, opening went from 402 MB of allocation to 206 MB, and peak memory from 642 MB to 445 MB. GRIB2 and NetCDF-4 already held exactly one copy and are unchanged. Part of #114; closes #411.
- **Opening a NetCDF file no longer reads it twice.** The editor asked the native layer for the dataset metadata and then built a separate reader for rendering, parsing and copying the whole file twice for a value the second reader could supply itself. It now builds one. On a 110 MB NetCDF-4 file, opening went from 103 ms to 40 ms.

- **Reading a NetCDF-4 file no longer re-walks it on every call.** The HDF5 reader re-derived structure it had already computed: decoding one variable walked the whole group tree to find its object header, walked that header for the shape and layout, then walked it again for the fill-value attributes, and resolving metadata walked every dataset twice more. Nothing was kept between calls, so the cost of reading a file with `D` variables grew as `D²`. The reader now remembers each file's traversal — the root address, the depth-first dataset list, every parsed object header, and each dataset's chunk index — and reuses it across metadata, shape, and value calls. A second pass over a file walks nothing at all. On the bundled fixtures, decoding every variable once fell from 42 to 8 structure walks (GOES-16 ABI, 5 variables) and from 110 to 12 (a 9-variable HDF5 file); a repeat pass costs zero. In memory this is only wasted CPU; over a byte-range transport each walk is a chain of dependent reads, so it is the whole cost.

### Rust API

- Crate descriptions on crates.io are corrected. `fieldglass-grib2` still described itself as decoding "simple-packing (DRS 5.0)", which stopped being true when the §5 census completed in 0.4.0 — it decodes every registered template. `fieldglass-core`'s described only its traits, where it also owns projection, reprojection and raster rendering. A crates.io description is fixed at publish time and cannot be edited afterwards, so both were wrong for the whole of 0.4.0.

- `fieldglass-grib1` gains a crate-level doc comment. It had none, so its docs.rs landing page was a bare module list where every sibling crate had an orientation. The four published crates now build their documentation without warnings; the dead intra-doc links that rendered as plain code spans are gone.

- `fieldglass_core::ByteSource` is new: the trait a decoder reads bytes through, so a reader can be handed a file it does not hold in memory. `Vec<u8>` implements it, and the NetCDF classic reader is migrated to it first. The shape is fixed by [ADR-0005](docs/decisions/0005-byte-access-and-the-remote-seam.md) — prefetch the ranges an operation needs, then decode synchronously — which is what keeps every decoder callable from a browser host without becoming async (#417, #438).

- `fieldglass_core::units::normalize_units` recognises `um`, `hr` and `dbar`, and renders `um` as `µm`. It also refuses any string containing `since` or `as` as a whole token, so a CF time coordinate (`minutes since 1870-01-01 00:00`) and a HYCOM date (`day as %Y%m%d.%f`) are left alone by rule rather than by the accident that their other tokens were unrecognised (#453, ADR-0007).

- `NetcdfVariableMeta` (napi) gains a `units` field, carrying the variable's CF `units` already typeset. The render panel had no other way to reach it (#453).

- `fieldglass_core::spatial_index::SpatialIndex` is new: nearest-cell lookup over an explicit list of cell centres, for the grid families that are a list of positions rather than a formula (NetCDF 2-D coordinates, GRIB2 §3.204, ICON §3.101). It builds a k-d tree over the centres **as unit vectors**, which removes the antimeridian and the poles as special cases and still gives the geodesic answer, since the chord `2·sin(θ/2)` increases strictly with the central angle. Build is 183 ms for a million cells and about 28 MB; 10,000 queries take 5 ms. A centre the file left non-finite is never returned, and a query further from every centre than the grid's own spacing is refused rather than snapped to a far cell. `GridGeometry` gains a `Lookup` variant carrying one, and `GridResampling` (`Any` / `NearestOnly`) is new alongside it: `warp` downgrades a bilinear request against a lookup grid rather than blending two cells that a tripolar fold may have put on opposite sides of the world, and it does that in one place so a caller cannot forget. `SpatialIndex::fingerprint` is the cheap identity a render cache should key on: `PartialEq` compares every centre, which is right but reads three million floats on a million-cell grid, and the cache asks that question on every repaint. `warp::SourceGrid` gains a `resampling` field, which is a **breaking change** for anyone constructing one.

- `fieldglass_core::projection::GridGeometry` is new: one typed value per grid family (`LatLon`, `Gaussian`, `Lambert`, `PolarStereo`, and `Unsupported { label }`), each carrying only the parameters its own family defines, with `kind`, `label`, `dims`, `forward`, `inverse`, `inverse_at`, `lonlat_bbox` and `proj4`. It replaces carrying every family's parameters side by side behind a `grid_type` string, where nothing stopped a caller reading `latin1` off a Gaussian grid. `proj4` is checked against PROJ 9.4.0 rather than by eye — the golden runs the whole geolocation through PROJ instead of Rust, and the two agree to 5e-10 degrees, which is half of PROJ's own printing quantum. `inverse_at` returns the inverse as a closure with the projection's constants computed once, which is what a warp wants: the one-shot `inverse` rebuilds them per call. `lonlat_bbox` delegates to `PlanarGridProjector::lonlat_bbox` rather than re-deriving the perimeter walk. It lives in the always-on `projection` module, not behind `render`, because the format crates take `core` with `default-features = false` and are the ones that will convert into it. `LatLonParams`, `GaussianParams`, `LambertParams` and `PolarStereoParams` gain `Serialize`/`Deserialize`.

- `fieldglass_core::detect_format` is behind a new default `fs` cargo feature, the only host-filesystem call in the four format crates. Depend with `default-features = false` on a target without a filesystem. `wasm32-unknown-unknown` compiles `std::fs` but fails every call at runtime, so the function would have silently degraded to guessing the format from the file extension rather than reading the magic bytes; the gate is what turns that into a compile error. `detect_from_bytes` is unaffected and is what a host without a filesystem should call. The feature is not a `no_std` switch: the crate still links `std` for float math. No change for any host taking default features.

- `PlanarGridProjector` gains a required `forward_xy(lat, lon) -> (f64, f64)` — the direction `inverse_lonlat` undoes — and provides `inverse(lat, lon) -> Option<GridIndex>`, which the four planar projectors previously each implemented for themselves. Two optional hooks carry what actually differed: `accepts(lat, lon)` (default `true`) for a projection that cannot place a point at all, and `snap_eps() -> SnapEps` (default `SnapEps::Cells(1e-9)`) for how far past a grid edge round-off may push an index before it is refused. `SnapEps` is new and has `Cells` and `Metres` forms; Lambert azimuthal equal-area is the one projector that needs `Metres`, because its round trip carries a real millimetre-scale error rather than float noise. The inherent `inverse` on `LambertProjector`, `PolarStereoProjector`, `LambertAzimuthalProjector` and `TransverseMercatorProjector` is unchanged and still callable without importing the trait. **Breaking for an out-of-tree implementor of `PlanarGridProjector`**, which must now supply `forward_xy`.

- `fieldglass_core::colormap::Palette` is new: the 256-entry RGBA lookup table, the already-transformed display domain (`t0`/`t1`), the scale mode, and the masked pixel, as one serialisable value. It is what `paint_grid_rgba` built internally, exposed so a GPU caller can upload the table and apply the same normalisation instead of writing a second colour implementation. `Palette::index` gives the exact byte the CPU painter emits; `Palette::normalise` is the `f32` form a shader mirrors, which agrees to within one table entry — though only because the arithmetic stays in `f64`; the type documents what a shader has to do to keep that bound. `paint_grid_rgba` and `scale_position` are unchanged in signature and in output.
- `ScaleMode` now derives `Serialize`/`Deserialize`, with the lowercase wire tags it already reported from `as_str` (`"linear"`, `"log10"`).
- `serde_json` is built with `float_roundtrip` across the workspace. Its default float parser is not correctly rounded, so an `f64` written by `to_string` could read back one ULP away.

- `fieldglass_core::SpatialIndex` gains `centre(i, j)` and `lonlat_bbox()`, and `GridGeometry::Lookup` now answers `forward` and `lonlat_bbox` through them (both previously returned `None`, pending #445). The index stores cell centres as unit vectors and derives degrees from them, so a longitude a file wrote unwrapped past 360° reads back as the same position with a different number. The bounding box is the extent of the centres, widened to the full 360° when they surround a pole and the enclosing longitude arc stops meaning anything (#445).

- `fieldglass_core::projection::GridResampling::applied_to(method)` is new: what a resampling request actually becomes on a given geometry. `warp` already applied this rule; it is exposed so a caller reporting what happened reads the same answer instead of echoing the request, which made a render summary name a bilinear blend that a lookup grid had never performed (#445).

- `fieldglass_netcdf::CurvilinearCoords` and `DatasetView::curvilinear_coords(var, y_dim, x_dim)` are new: the CF `coordinates` attribute resolved to a 2-D latitude/longitude pair, or `None` when it names no usable one. Names are kept only if they resolve to a 2-D variable over exactly the two dimensions being drawn — the attribute may name more than the pair, and RTOFS writes `"Longitude Latitude Date"` (#445).

- **`fieldglass_grib2::gds::GridDefinitionSection` is no longer `Copy`.** It gains `row_widths: Vec<u32>`, §3's optional list of numbers read as the `PL` row widths of a reduced grid, which is one entry per row and cannot be a fixed-size field. Read it through the new `points_per_row() -> Option<&[u32]>`, which mirrors `fieldglass_grib1::GridDescription::points_per_row` and answers only where the list really is a per-row point count (a reduced Gaussian template, exactly `Nj` entries, and an interpretation of `1` or `2` from Code Table 3.11). The struct is still `Clone`; a caller that relied on an implicit copy needs `.clone()` or a borrow (#503).

- `fieldglass_grib2::gds::GridDefinitionSection::dimensions` now answers for a reduced Gaussian grid, reporting `(max(PL), Nj)` — the raster the rows expand into — where it previously returned `None`. That is the shape `fieldglass_grib1` has always reported for the same grid, and it is derived rather than stated: `size_label` remains the file's own answer (`N32`, `O32`) and is what a display should prefer. `decode_message_values` returns the `sum(PL)` stored field, not the raster; widening is the caller's step (#503).

- `fieldglass_core::expand_reduced_to_regular` is new — moved from `fieldglass_grib1::gds`, where GRIB2 could not reach it. `fieldglass_grib1::expand_reduced_to_regular` still resolves, as a re-export. Alongside it, `fieldglass_core::reduced_raster_width` gives the widest row, and `fieldglass_core::reduced_raster_lon_last(lon_first, width)` gives the last column's longitude of the expanded raster. The last of those is deliberately *not* the message's declared last-point longitude: under §3's interpretation code 1 each row spans the full circle in its own number of steps, and ECMWF writes `lo2` from the `4N`-wide reference grid, which for an octahedral grid is narrower than the widest row (#503).

- `fieldglass_grib2::gds::GridDefinitionSection::template_name` returns `"reduced_gaussian"` for a reduced Gaussian grid, where it returned `"gaussian"` for both variants before. Template 3.40 covers both, but they are not the same grid — one has a constant `Ni`, the other a `PL` list — and eccodes names them apart as `regular_gg` and `reduced_gg`. `fieldglass_grib1` already reported `"reduced_gaussian"`, so the two crates now agree; a caller matching on the string needs the second arm (#503).

- `fieldglass_grib2::undo_alternate_reduced_rows` is new: the ragged sibling of `undo_alternate_rows`, for a reduced grid whose rows have no single width. It runs on the stored field, before expansion (#503).

- `fieldglass_grib2::gds::GridDefinition::size_label` and `fieldglass_grib1::GridDescription::size_label` are new, returning `Option<String>`. They give the name a file puts on its own grid where `Ni × Nj` is not how it is described: a spectral field by its truncation (`T63`, or the pentagonal triple when `J`, `K` and `M` differ), a bi-Fourier field by its resolution pair, a HEALPix field by `Nside`, a reduced Gaussian grid by `N32`/`O32`. A caller showing a size should prefer it and fall back to `dimensions` — for a reduced grid GRIB1 answers both, and the raster it reports is one the crate derives rather than one the file states (#416, #500).

- `fieldglass_core::is_octahedral_pl` is new: whether a reduced Gaussian grid's `PL` row widths describe an octahedral grid (`O1280`) or a classic one (`N320`). It is eccodes' own rule from `OctahedralGaussian.cc` — every step `0`, `+4` or `-4`, ordered as rise, at most one plateau, fall — rather than the shortcut of comparing the equatorial row against `4N + 16`, which reads one row and would accept a grid octahedral only at its equator. Steps are taken in `i64` so a width near `u32::MAX` from a hostile file cannot wrap into a valid-looking step. It answers as eccodes does on a list of fewer than two rows (`true`, there being no step to disagree about), so it never diverges from the oracle it is checked against; deciding what counts as a grid is the caller's job. `GaussianTemplate` gains `is_octahedral`, classified at parse time (#500).

- `fieldglass_grib2::lookup_parameter` takes an `Originator` (the §1 originating centre, sub-centre and local table version) as its first argument. Codes WMO reserves for local use — 192-254 in any of discipline, category or parameter number — are offered to that centre's table before the WMO set; everything else resolves exactly as before. `IdentificationSection::originator()` builds one from a parsed message. No centre tables are registered yet (#424-#426), so resolution is unchanged for every input today.
- `fieldglass_grib1::tables::lookup_centre` is gone, replaced by `fieldglass_grib1::tables_cct::lookup_centre`. It returns `Option<&'static str>` rather than falling back to the string `"Unknown centre"`, matching the GRIB2 side; render the numeric id when it returns `None`.
- `fieldglass_grib2::lookup_centre` keeps its signature but is now re-exported from the generated `tables_cct` module, and its names are WMO's own — `"European Centre for Medium Range Weather Forecasts (ECMWF) (RSMC)"` rather than the previous curated spelling.
- `fieldglass_core::cct_tables::lookup_sub_centre(centre, sub_centre)` is new. It takes both codes: sub-centre numbering is per-centre, so a lookup on the sub-centre alone cannot be correct.
- `Hdf5Probe` carries a private traversal memo, so it is no longer constructible as a struct literal — use `Hdf5Probe::new(superblock_version, offset_size, length_size)`. Its three superblock fields are unchanged and still public; the memo takes no part in `Clone`, `PartialEq`, or `Debug`. A new `Hdf5Probe::traversals()` reports how much of a file a probe has actually walked, for tests and measurement.
- A probe is bound to its own file, which the traversal functions taking `bytes` and `probe` separately now enforce as far as they cheaply can: the memo binds to its slice length on first use and steps aside for any other length, so pairing a probe with a different file is slow rather than wrong. Two files of exactly equal length are indistinguishable that way and still alias.

## [0.4.0] — 2026-08-23

### Added

- **GRIB2 true matrix-of-values fields (template 5.1, `matrixBitmapsPresent = 1`) now decode.** This completes template 5.1: the genuine `NR×NC` matrix at every grid point, delimited by secondary bitmaps (historically ECMWF 2-D wave spectra), decodes through `Grib2Reader::decode_matrix_message` into a flattened per-point matrix field. Stock eccodes cannot handle this variant — it divides by zero and crashes — so, like the GRIB1 form, it follows the GRIBEX interpretation and shares the reshape with the GRIB1 decoder (now factored into `fieldglass-core`). Correctness is pinned by hand-constructed known-field unit tests and a cross-edition check: the same logical field encoded in GRIB1 and GRIB2 decodes identically through the two independent readers. With this, Fieldglass decodes every registered GRIB2 §5 packing template. Closes #306.
- **GRIB1 and GRIB2 spectral fields now render in the viewer.** Building on the inverse spherical-harmonic transform, a spherical-harmonic message (GRIB2 §3.50 packing 5.50/5.51, or the GRIB1 equivalent) is now rendered by synthesizing it onto a global regular lat/lon grid (0.5°, 720 × 361) and painting that grid through the normal pipeline — so it displays, reprojects, contours, and probes like any other field. Previously such a message showed "Render not available — grid dimensions unknown"; it now offers a Render button. The coefficients describe a band-limited function rather than a sampled grid, so they are evaluated at every point of that grid exactly — a truncation smaller than the grid is not interpolated up to it. No other viewer in the ecosystem renders spectral fields; both GRIB1 and GRIB2 go through the shared `fieldglass-core::sht` engine. Closes #303.
- **Spectral fields can now be synthesized back onto a lat/lon grid (inverse spherical-harmonic transform).** ECMWF/IFS spectral GRIB fields store spherical-harmonic coefficients, not grid values, and no tool in the ecosystem turns them back into a grid (Panoply and netcdf-java report "Unsupported GDS type = 50"). Fieldglass now performs the inverse transform: `Grib2Reader::synthesize_spectral_message` evaluates the field at any regular lat/lon grid via a new `fieldglass-core::sht` engine (a fully-normalized associated-Legendre recurrence plus the real-field reconstruction). The numerics are validated against ECMWF's definitive spectral definition — exact analytic single-coefficient cases plus a full T63 field oracle (cross-validated against pyshtools during development) — since eccodes itself cannot synthesize a grid from spectral coefficients. This is the engine behind rendering spectral fields; the render-panel display wiring is the next step. Part of #303.
- **GRIB2 matrix-of-values fields (template 5.1) now decode in their flat form.** DRT 5.1 (`grid_simple_matrix`) is an experimental template for an `NR×NC` matrix at each grid point. In its common `matrixBitmapsPresent = 0` form the §7 payload is one simple-packed value per grid point — `NR`/`NC` and the coordinate-function coefficients are descriptive §5 metadata — so Fieldglass now parses that metadata and decodes and renders the field exactly like template 5.0, cross-validated against eccodes 2.34 value for value. The true per-point matrix (`matrixBitmapsPresent = 1`, delimited by secondary bitmaps) is the variant stock eccodes can neither encode nor decode; it is rejected with a clear error rather than mis-decoded. Part of #306.
- **GRIB2 bi-Fourier spectral fields now decode to their coefficients.** The ACCORD/ALADIN/AROME limited-area spectral models store fields as bi-Fourier coefficients (§3 templates 3.61/62/63, packing template 5.53) — four coefficients per `(i, j)` wavenumber pair over a rectangle, ellipse, or diamond truncation. Fieldglass now decodes them through `Grib2Reader::decode_bifourier_message`: the coefficients inside the unpacked sub-truncation are read as raw IEEE floats (32- or 64-bit) and the rest are simple-packed after division by the bi-Fourier Laplacian operator `(i²+j²)^P`, matching eccodes' `DataG2BifourierPacking` coefficient for coefficient (cross-checked against eccodes 2.34 across the three truncation shapes and both float precisions). Like the spherical-harmonic forms these are coefficients in wavenumber space, not values on a grid, so the message does not render yet — an inverse bi-Fourier transform is a follow-up — and the scalar decode path now points callers at the bi-Fourier entry point. Closes #304.
- **GRIB2 second-order packed fields now decode and render.** Templates 5.50002 (`grid_second_order`) and 5.50001 (`grid_second_order_no_boustrophedonic`) carry the GRIB1 general-extended second-order codec into GRIB2 — common in ECMWF MARS-derived files. Fieldglass now decodes both: §5 supplies the group-descriptor bit widths and the spatial-predictor-differencing (SPD) seeds, §7 supplies the group widths, lengths, first-order references, and second-order offsets, and the SPD inverse (now shared with the GRIB1 second-order decoder in `fieldglass-core`) reconstructs the field before the `R` / `E` / `D` transform. Alternating-row (boustrophedonic) ordering — the `secondOrderFlags` bit that 5.50002 can set — is undone on decode. Because the output is one value per grid point, projection, overlays, and the rest of the pipeline work unchanged. Cross-checked against eccodes 2.34 value for value, including the boustrophedonic path. Closes #307.
- **The rendered plot can now be exported as a PNG.** The render panel gains an "Export PNG…" button that composites the current view — the map raster, the overlays (contours, coastlines, borders, graticule), the colorbar, and the title — into a PNG at the field's native resolution and writes it to a location you pick, with a filename derived from the parameter and slice. The map raster and overlays are copied exactly from the on-screen canvases; the colorbar and title are redrawn on the export canvas. Works for GRIB and NetCDF renders, from a background tab too. Closes #243.
- **GRIB2 spectral (spherical-harmonic) fields now decode to their coefficients.** ECMWF IFS analyses and other spectral-model output store a field as spherical-harmonic coefficients (§3 template 3.50) rather than grid values. Both spectral packings — `spectral_simple` (§5 template 5.50) and `spectral_complex` (5.51, the ECMWF IFS form, whose §7 stores a sub-truncation of raw IEEE floats followed by a Laplacian-rescaled simple-packed remainder) — now decode through `Grib2Reader::decode_spectral_message` in the Rust API, each checked coefficient for coefficient against eccodes on a T63 field, mirroring the existing GRIB1 spectral support. The coefficients are not values on a grid, so such a message still does not render as a 2-D image — recovering a grid needs an inverse spherical-harmonic transform, which is a follow-up — and `decode_message_values` now reports a precise reason pointing at the spectral entry point instead of a bare "no dimensions" error. Part of #302.

Either writes the field to a file in one of two layouts you pick: a long `lat,lon,value` table (one row per grid point) or a 2-D matrix of values. Missing points come out as empty value cells, and a large export is confirmed before it is written. Under the hood, `fieldglass-core` gains a `csv` module (`field_to_csv_matrix` / `field_to_csv_long`, formatting values in the shortest round-trippable form) and the napi bindings an `exportCsv` on the GRIB1, GRIB2, and NetCDF handles. Reduced-grid and projected long-format export are still to come. Part of #244.
- **GRIB2 pre-standard local image packings now decode.** Two local-use data-representation templates carry historical NCEP data with a layout identical to a registered image packing: 5.40000 (early JPEG 2000, identical to template 5.40) and 5.40010 (early PNG, identical to template 5.41). Fieldglass now decodes both through the existing JPEG 2000 and PNG codecs. eccodes ships no definition for 5.40010 and cannot decode it at all, so this is one more packing Fieldglass reads that stock eccodes cannot. Part of #307 (the ECMWF second-order local templates 5.50001 / 5.50002 remain).
- **GRIB2 log-preprocessing packed fields now decode.** Template 5.61 (simple packing with logarithmic pre-processing) stores the natural logarithm of the field under ordinary simple packing. Fieldglass now decodes it — simple unpacking followed by `Y = exp(X) − B`, where `B` is the pre-processing parameter — so these fields render instead of reporting an unsupported template. The template is experimental with no known operational producer; this completes another entry in the GRIB2 §5 packing census. Both the `B = 0` (positive field) and `B ≠ 0` branches are checked against eccodes. Closes #305.
- **GRIB2 run-length packed fields now decode and render.** JMA ships its 1 km radar, rain-gauge analysis, and nowcast products as run-length packing (DRS template 5.200): runs of quantised level indices that resolve through a level-to-value table, with level 0 marking missing. Fieldglass now decodes it, so these fields render instead of reporting an unsupported template. Because the output is one value per grid point on a regular lat/lon grid, projection, overlays, and the rest of the pipeline work with no further changes. Cross-checked against eccodes. Closes #301.
- **Click a rendered field to read its value.** A point-probe readout (#172): clicking anywhere on the image reports the geographic point under the cursor and the field's decoded value and units there — ncview-style interrogation. It reproduces the render's own per-pixel map (output pixel → lat/lon → source grid cell), so the number is exactly the one the colour shows, on every projection (source, the lat/lon-box targets, and the azimuthal/world targets — a click off the globe reports nothing). Works for GRIB and NetCDF. The optional 1-D line plot through the point is still to come. Part of #172.
- **Fields can now be compared as a difference map.** The render panel's Compare row picks a second field and an operation — `A − B`, `B − A`, `A + B`, `mean(A, B)`, or `A / B` — and renders the combined field. The difference map (`A − B`) is Panoply's flagship workflow: it reads an anomaly, a bias, or the change between two time steps at a glance. For GRIB, Field B is another message in the file; for NetCDF, it is the same variable at a second slice (its own set of dimension steppers — the two-time-steps or two-levels case). Missing data in either field is missing in the result, and a divide-by-zero drops out rather than painting a spurious value; the two fields must sit on the same grid. The combined field rides the normal pipeline, so projection, overlays, palette, scaling, and manual bounds all work on it. Off by default. Closes #239.
- **Contour lines can be drawn over any rendered field.** A Contours toggle in the render panel's Overlay row traces isolines of the field — the standard way to read a pressure or height pattern — on the same canvas as the coastlines, following the map through every projection. Levels are chosen automatically (round 1/2/5 × 10ⁿ values, à la Panoply), or set by a manual interval; the isolines break cleanly around missing data. A "contours only" mode hides the colour raster so the lines read on a blank background, and the line colour and weight are adjustable. Under the hood, `fieldglass-core` gains a `contour` module (marching squares in grid space) and the napi bindings a `projectContours` that geolocates the grid-space isolines through each grid's forward map and runs them through the same overlay-projection path the coastlines use. Contours are available for the lat/lon family (regular lat/lon, Mercator, rotated lat/lon, Gaussian); projected and reduced grids report a clear "not yet supported" message for now. Closes #238.
- **The reader API can now combine two fields into a difference, sum, ratio, or average.** The Rust `fieldglass-core` crate gains `combine_fields` and a `CombineOp` for element-wise `A − B`, `B − A`, `A + B`, `mean(A, B)`, and `A / B`, with missing propagating from either input and a divide-by-zero falling out as missing. The napi bindings expose it as `renderGridCombined` (GRIB) and `renderSliceCombined` (NetCDF), which decode two fields on the same grid, combine them, and render the result through the ordinary pipeline — so projection, overlays, palette, scaling, and manual bounds all apply to the computed field with no special casing. Fields must sit on identical grids; a mismatch is a clear error. This is the engine behind the difference-map workflow the render panel's Compare row rides on. Part of #239.
- **Fields can now be coloured on a log10 scale.** The render panel painted every field on a linear scale, which flattens quantities that span orders of magnitude — precipitation, aerosol optical depth, chlorophyll — into the bottom of the colour ramp. A new Log₁₀ toggle in the Colors row maps colour by the base-10 logarithm of the value instead, so each decade gets its own share of the ramp. Non-positive values have no logarithm and render as missing (transparent), and the colorbar keeps its labels in the true, unlogged data units. Log needs a positive floor, so the toggle is disabled with a hint until the range starts above zero, either because the field is all-positive or because a positive manual minimum is set. Linear stays the default. Closes #235.

### Fixed

- **The dormant in-viewer P1 edit no longer carries the wrong number.** In-viewer editing of a GRIB1 forecast period is switched off (it waits on general PDS field editing), but the input it would render was pre-filled with the *normalised* forecast hours while the edit writes the raw P1 octet. Under a 3-hourly unit the box read 12 for a P1 of 4, so opening it and saving an untouched value would have tripled the lead time. The box now carries the octet it writes, and a message whose P1 spans two octets (time-range 10, where no single-octet edit is meaningful) stays read-only.
- **A forecast lead too large to express in hours no longer reads as the analysis.** Normalising a GRIB2 forecast time to hours can overflow the whole-hours field — a step given in seconds or minutes far enough out. It fell back to 0, filing a far-future step next to the analysis time, which is the one reading that column exists to support. It now saturates, so a too-large lead stays a large lead. A unit with no clean conversion to hours still reports none; the display string carries the raw value and its label.
- **GRIB1 forecast times now read GRIB1's own unit table.** The lead time was converted with GRIB2's Code Table 4.4, but GRIB1 uses ON388 Table 4, and the two disagree where it matters: code 13 is 15 minutes in GRIB1 and a second in GRIB2, code 14 (30 minutes) has no GRIB2 counterpart, and a GRIB1 second is code 254. A two-hour nowcast step in 15-minute units therefore displayed as `+0h`, a two-hour lead in seconds as `+7200h`, and a six-month mean as `+6h` — a lead time invented from the unit code. Each unit now converts through its true length, sub-hourly steps round to the nearest hour instead of truncating, and a unit with no fixed length in hours (month, year, decade, normal, century) keeps its own number and label rather than being printed as hours. The Rust `fieldglass_grib1::forecast_hours` returns `Option<i32>` to say so.
- **A GRIB1 forecast whose lead spans both P1 octets now reports that lead in the hours column too.** Time-range indicator 10 stores P1 as a single 16-bit value across octets 19 and 20. The display string assembled it, but the numeric forecast-hours field read octet 19 alone, so a 12-hour forecast showed "+12h" beside a lead of 0. Both now read the same value.
- **The exported PNG no longer clips its title and reference time.** The image was sized from the map raster and its colorbar alone, so a field whose raster is narrower than its own header ran the header off the right edge — a synthesized spectral grid is 256 pixels wide, well under the width of the line naming its parameter, level, and reference time. The export now measures the header and widens the image to fit it; a wide field exports exactly as before.
- **A level with no value is no longer named twice in the render panel header.** For level types whose numeric value carries no information, the decoder reports the surface name as both the level and the level type, and the header joined the two — reading "Ground or water surface Ground or water surface". It now names the level once, in the panel and in the exported PNG.
- **Exporting a GRIB field as PNG now writes a file.** The Export PNG button sits in the panel HTML both render panels share, so a GRIB render offered it — but only the NetCDF panel listened for the export, so on a GRIB field the button did nothing: no save dialog, and a status stuck on "Exporting PNG…". The GRIB panel now routes the export to the same handler, so it saves, cancels, and reports failures exactly like a NetCDF slice.
- **The render panel no longer says "Exporting PNG…" forever.** The panel showed that status the moment it handed the image to be saved and never took it down, so a finished export, a cancelled one, and one still in flight all looked identical. The save dialog and the result notification live outside the panel, which had no way to learn the outcome; it is now told, and reports the file it wrote, a cancellation, or the reason it failed.
- **Contour lines no longer break at the seam meridian on a global field.** On a grid that wraps the globe, isolines stopped one cell short of the wrap, leaving a gap along the seam — at 0°/360° for a field whose grid starts there. The marching-squares pass never looked at the cell between the last column and the first, and the grid-to-lon/lat map clamped anything past the last column, so a seam vertex collapsed onto it. Both now wrap, and the interpolation crosses the seam gap eastward instead of sweeping back across the map. This is the same treatment the raster resampler already applied, which is why a global field could paint across the seam while its contours stopped short of it. Regional grids are unaffected: the wrap is used only where the grid is detected as global, since wrapping a bounded grid would draw a spurious line from its east edge back to its west one. Rotated lat/lon grids keep the old behaviour for now — a rotated row traces a small circle whose longitude does not advance evenly, so closing its seam needs the interpolation done in rotated coordinates.
- **Spectral fields can now be reprojected from the render panel.** A spherical-harmonic message rendered on its synthesized lat/lon grid was stuck on "Source projection", under a note reading "Reprojection isn't available for spherical_harmonic grids yet." The engine reprojected such a field correctly all along — every target rendered through the native API — but the panel gated its projection picker on the message's own grid, which a spectral message does not have. It now keys on the synthesized grid, so the full set of targets is offered for GRIB1 and GRIB2 spectral fields alike. Bi-Fourier messages, which also lack a grid but do not render at all, correctly keep the source-only picker.
- **Probing a global field near the antimeridian now reads its value instead of "no data".** On a reprojected view of a grid that wraps the globe (any world or lat/lon-box projection of a lat/lon, Mercator, or Gaussian grid), clicking a painted pixel in the seam past the last column — a GFS 0.25° click near 360° longitude, say — reported "no data" even though the pixel was coloured. The probe rounded the wrapped column index off the edge of the grid; it now wraps it back to the first column exactly as the renderer does, so the readout matches the colour under the cursor. Closes #332.
- **Exporting a projected field as long-format CSV now explains the real limitation.** Long-format CSV needs per-point coordinates, so it is offered only for the lat/lon grid family — but a Lambert or polar-stereographic field exporting as Long failed with "contours not yet supported", the wrong feature's message, and no hint that the Matrix layout works. The error now names the long CSV format and points at the Matrix layout instead. Closes #337.
- **A contour error no longer overwrites the render summary.** When contours could not be drawn on a grid (projected and reduced grids aren't wired yet), the "Contours: …" message replaced the dimensions-and-range summary and stayed there until the next full render — even after the Contours box was unchecked. The message now shows on its own line, so the summary is left intact, and it clears when contours are turned off or re-requested. Closes #338.
- **The exported PNG colorbar labels the log10 midpoint correctly.** On a log-scaled render the colorbar's middle tick was labelled with the arithmetic mean of the range, but the colour at mid-height is the geometric mean — so a 1…100 field labelled its midpoint "50.50" instead of "10.0". The exported PNG now labels it with the geometric mean under log10 scaling, matching the colour beneath it; linear renders are unchanged. Closes #331.
- **Probing and contouring a difference map now read the difference, not field A.** With a Compare operation active, the image shows the combined field (A − B, a sum, a ratio, …), but clicking to probe reported field A's value there and the contour lines traced field A's isolines over the difference raster. Both now run on the same combined field the image shows, for GRIB and NetCDF. Closes #329.
- **Spectral fields now support every feature, not just rendering.** A spherical-harmonic message has no grid of its own, so exporting it as CSV, probing a value, drawing contours, overlaying coastlines, or comparing it against another field all failed with an internal error while only the map itself rendered. These now work on the same synthesized lat/lon grid the render already uses — the field is synthesized once at the decode seam and every feature runs against it. Closes #330.

Pre-releases stay git-only, since crates.io has no pre-release channel. Closes #229.

Changing a layer's colour or weight repaints immediately without reprojecting. The data is Natural Earth 1:110m (public domain) and ships with the extension, so nothing is fetched at run time. Closes #237.
- **A colormap picker with eight colormaps.** The render panel used to paint every field in viridis, with no way to change it. It now offers five sequential maps (viridis, plasma, cividis, turbo, grayscale) and three diverging ones (red–blue, brown–teal, cool–warm), each of which can be reversed. Diverging maps suit anomaly and difference fields, where what matters is which side of the midpoint a value falls on. Viridis stays the default, so an existing view renders exactly as before. The colours are applied in Rust and the legend strip is drawn from the same table that paints the grid, so the two can't disagree. Closes #234.
- **Three new world map projections for global fields.** The render panel's projection picker adds Mollweide, Robinson, and Equal Earth alongside the existing equirectangular, Web Mercator, orthographic, and polar-stereographic targets. Mollweide and Equal Earth are equal-area, so a field's features cover map areas in true proportion; Robinson is the compromise projection familiar from wall maps and atlases. Each takes a central-meridian control to recentre the map. Closes #242.
- **NetCDF-4 files that store their variables in groups now show and render those variables.** Metadata resolution previously read the root group only, so a file that puts everything under groups — Sentinel-5P and other ESA Level-2 products (`/PRODUCT/...`), NASA GPM IMERG (`/Grid/...`), OMI-style HDF-EOS layouts — showed an empty or near-empty variables table even though the underlying structure was fully supported. Fieldglass now descends into every group, lists each variable and dimension with a path-qualified name (`/PRODUCT/qa_value`), resolves a variable's dimensions even when they live in an ancestor group (the netCDF scoping rule), and decodes and renders grouped variables like root ones. Checked against the Unidata `netCDF4` library. Closes #219.
- **NetCDF-4 / HDF5 files written in the "latest format" now decode more chunked variables.** Value decode previously read only the version-1 B-tree chunk index, so a file written by a recent libhdf5 (the "latest format") often reported an unsupported-layout error. Fieldglass now also reads the version-4 single-chunk and fixed-array indexes — the common cases for a one-chunk variable and a fixed-shape multi-chunk variable — the extensible-array index used for a variable with an unlimited dimension (the growable time-series case), each for both filtered and unfiltered chunks, the implicit index used for a fixed-shape, early-allocated, unfiltered variable whose chunks are stored contiguously with no on-disk index, and the v2-B-tree index used for a variable with more than one unlimited dimension. The newer version-5 layout message that libhdf5 2.0 writes for a filtered variable is read too. Everything is checked against `h5py`. Closes #216.
- **GRIB2 complex-packed fields with inline missing values now decode.** Sparse NCEP products such as the National Blend of Models (NBM) and precipitation type mark missing points inside the packed data (missing-value management, templates 5.2 / 5.3) instead of using a bitmap. Fieldglass now decodes both management modes (primary, and primary + secondary substitutes) and masks the missing points exactly like bitmap points, so these fields render instead of reporting an unsupported-template error. Fields whose groups are split row by row, which templates 5.2 / 5.3 also used to reject, decode too. Both are checked against eccodes, and the NBM file in the sample corpus now renders. Closes #217.
- **GRIB2 constant complex-packed fields now decode.** Some encoders write an all-same-value field under templates 5.2 / 5.3 as zero groups, which used to be rejected as malformed. Fieldglass now decodes zero groups as a constant field equal to the reference value, matching eccodes 2.42 and later, and the result is checked against eccodes. Closes #222.
- **Polar stereographic and Mercator WRF output now reprojects onto the map.** WRF `wrfout` rendering previously recognised only the Lambert Conformal projection (`MAP_PROJ = 1`); polar-region domains (`MAP_PROJ = 2`, polar stereographic) and tropical domains (`MAP_PROJ = 3`, Mercator) fell back to an unprojected source-only image. Fieldglass now reads both from the same global attributes and reprojects them through the projectors the GRIB paths already use, checked against independently computed coordinates. Closes #220.
- **Unrotated lat-lon WRF output now reprojects onto the map.** WRF's lat-lon projection (`MAP_PROJ = 6`), used for global and some regional domains, previously fell back to an unprojected source-only image. An unrotated domain (`POLE_LAT = 90`) is a plain regular geographic grid, so Fieldglass now geolocates it from its corner coordinates and reprojects it like any other lat/lon grid, checked against independently computed coordinates. Rotated domains (`POLE_LAT` other than 90) still render source-only, because the mapping from WRF's rotation parameters onto a rotated pole is not cleanly documented. Closes #226.

### Fixed

- **GRIB1 spectral files now open in the viewer instead of failing with "the editor could not be opened".** A spherical-harmonic (spectral) message has no grid, so its grid size and corner coordinates are absent. The message table read those absent fields with a check that missed the way the reader reports "not present", so building the table threw and the whole editor failed to open with an empty table. Fieldglass now handles the absent fields correctly: the table lists a spectral message with its packing and a dash for size and bounds, and Render is offered only for messages that have a grid. Closes #288.
- **The source projection no longer shows many grids upside-down until you check Flip Y.** The source view painted grid row 0 at the top of the image without regard to the grid's scan direction. Grids that scan south to north — common in regional Lambert and polar-stereographic output, such as the National Blend of Models — therefore came out vertically flipped, and only reprojecting to another target, or manually toggling Flip Y, set them right. The source view now orients the raster from the scan direction, so it is upright by default; Flip Y is now a genuine override rather than a routine fix. Grids that already scanned north to south are unchanged. Closes #286.
- **Grids that scan alternate rows in opposite directions no longer render as a mirrored, noisy field.** Some products, including the National Blend of Models (NBM), store their rows boustrophedon-style: the first row runs west to east, the next east to west, and so on (scanning-mode flag bit 4). The decoded values were correct, but every second row was left reversed, so the image came out as a scrambled left-right mirror of itself with a noisy seam between each pair of rows. Fieldglass now flips those rows back at the point of decode, so the field is laid out west to east on every row. The value range was already right, which is why the earlier check missed it; the fault was purely in where each point landed.
- **Overlay lines on the ±180° meridian no longer jump to the wrong edge of the map.** A coastline or graticule vertex sitting exactly on the ±180° meridian was placed on the opposite edge of the map from the one it belongs to. On Mollweide this drew a thick horizontal line clear across the map at about 71°N, through Wrangel Island, and another across Antarctica; elsewhere the stray vertex was quietly discarded instead, which nicked the Siberian coast at the ±180° meridian, dropped one small island outright, and clipped the ends of every parallel on a graticule finer than 30°. The equirectangular and Web Mercator views dropped the same vertices on a global window. Such a vertex now stays on its own edge in every view.
- **Coastlines no longer streak across a recentred world map.** When a world map projection was recentred (the central-meridian control), a coastline that crossed the map's new seam could be drawn as a line straight across the map instead of stopping at the edge — most visible on Mollweide above about 70° latitude, where recentring moves the seam onto Arctic or Antarctic coast. The overlay decided where to break a line from how far apart two points landed on screen, which misreads a seam crossing on a map that narrows toward the poles. It now breaks the line by the points' longitudes instead, so the break is correct on every projection whatever its shape.
- **Lambert and polar-stereographic grids are now placed on the Earth the message declares, not a fixed one.** The projection assumed a single spherical Earth radius (6 371 229 m) for every message. GRIB1 declares 6 367 470 m, GRIB2 declares its own shape per message, and WRF projects on 6 370 000 m — so a field could land kilometres from where it belongs. On the CMC polar-stereographic sample the far corner of the grid sat 3.5 km from where eccodes puts it, and the coastline overlay drifted from the data beneath it by the same amount. Fieldglass now reads the declared earth shape (GRIB1's flag, GRIB2's `shapeOfTheEarth`, WRF's own sphere) and projects on it, matching eccodes' point iterator across the whole grid. Oblate shapes use the spheroid's mean radius, within ~0.1 % of the true figure; true ellipsoidal projection is a follow-up. Closes #271.
- **The outermost row and column of a Lambert or polar-stereographic field no longer drop out of the render.** A grid point lying exactly on the grid's edge could come back from the projection arithmetic a fraction of a billionth of a cell outside it, which the bounds check read as off-grid and painted as background. The two projections now absorb that rounding, as the rotated lat/lon one already did.
- **A corrupt GRIB1 second-order message can no longer decode to wrong values.** The shared bit reader returns its result as a 32-bit integer, but nothing stopped a caller asking for more than 32 bits, which silently dropped the extra high bits. A malformed second-order-packed field could declare a per-group value width above 32 and hit that path. The reader now rejects a request for more than 32 bits, so such a file is reported as an error instead of rendering incorrect data.

The metadata viewer now populates the same dimensions / variables / global-attributes tables for NetCDF-4 / HDF5 files as it already did for classic ones. Resolution covers the file's root group; variables in nested groups are a follow-up. The resolved names and dimension lists are checked against the canonical Unidata netCDF4 library (`ncdump`). Closes #174.
- **Classic NetCDF fields now render as a 2-D image.** For a classic file on a regular lat/lon grid, Fieldglass draws a 2-D slice of a variable in the render panel. It detects the latitude and longitude axes from CF conventions on the coordinate variables, lists the renderable variables, and gives a slice picker: choose the variable and the image (X / Y) axes, and step through the remaining dimensions (time, level) with per-dimension index controls. The slice synthesises a regular lat/lon grid from the coordinate arrays and feeds the existing render pipeline, so the projection picker (source, equirectangular, Web Mercator, orthographic, polar stereographic), the colormap, and the coastline / graticule overlays all work the same as for GRIB. NetCDF-4 / HDF5 and curvilinear (2-D coordinate) grids are tracked follow-ups. Closes #122.
- **NetCDF-4 / HDF5 fields now render as a 2-D image too.** The slice picker, axis detection, and synthesised-grid rendering that classic files gained now work for NetCDF-4 / HDF5 files on a regular lat/lon grid, using the dimensions and coordinate variables resolved from the dimension-scale convention. Both backings share one rendering path, so the projection picker, colormap, and overlays behave identically; the only remaining gap is curvilinear and projected grids. Closes #169.
- **WRF and GOES NetCDF fields now reproject onto the map.** Two common model outputs are regular grids in a projected coordinate system rather than plain lat/lon. WRF `wrfout` files carry a Lambert Conformal projection in their global attributes (`MAP_PROJ`, `TRUELAT1`/`TRUELAT2`, `STAND_LON`, `DX`/`DY`); GOES satellite imagery carries a CF `geostationary` grid mapping with scan-angle `x`/`y` coordinates. Fieldglass now reads both and reprojects them through the same Lambert and geostationary projectors the GRIB2 path uses, so they render with coastlines in the right place (off-disk pixels on a GOES image stay transparent). Both are cross-checked against an independent geolocation oracle. Irregular curvilinear grids (ocean tripolar, swath) remain a follow-up. Closes #168.
- **Packed NetCDF fields now render in real units.** Many NetCDF files store a field as compact integers with a `scale_factor` and `add_offset` to recover the physical values — the convention GOES, MERRA-2, and ERA5 use. Fieldglass now applies that conversion to the data it renders, so the image and the colorbar labels read in the variable's real units (kelvin, radiance, …) instead of raw integer codes. It also honours a field's `valid_range` / `valid_min` / `valid_max`, masking out-of-range points like the canonical netCDF library does. Both the classic and NetCDF-4 / HDF5 backings share one path, cross-checked against the netCDF4 library. Closes #184.
- **GRIB2 Mercator and Lambert grids now reproject onto the map.** The projection picker already reprojected GRIB2 polar stereographic grids; it now also handles GRIB2 Mercator (§3.10) and Lambert Conformal (§3.30) source grids, so products on those grids reproject into the flat targets the same way their GRIB1 counterparts do. Closes #119.
- **GRIB2 rotated lat/lon grids now reproject onto the map.** Environment Canada (HRDPS/RDPS) and DWD (ICON-EU), among others, publish on a rotated lat/lon grid (§3.1) whose coordinates sit on a tilted pole. Fieldglass now unrotates those grids so they reproject into the flat targets with coastlines in the right place, matching how eccodes places the points. Closes #120.
- **GRIB2 space-view (geostationary) grids now reproject onto the map.** Geostationary satellite imagery stored as GRIB2 §3.90 is a regular grid in the satellite's scan-angle space, which previously had no projector and could not reproject. Fieldglass adds a geostationary projector that maps each output point through the satellite's view of the Earth ellipsoid, so §3.90 grids reproject into the flat targets with coastlines in the right place and off-disk pixels stay transparent. The same projector will serve GOES NetCDF imagery in a later release. Closes #176.
- **Geostationary sector products now frame to their own extent.** When a cropped §3.90 sector (a GOES CONUS or mesoscale, or a Meteosat sector) reprojects into a flat lat/lon target, Fieldglass now derives the map frame from the sector's on-disk extent instead of defaulting to the whole satellite-visible hemisphere, so the sector fills the view rather than sitting in a hemisphere of empty space. Full-disk products, whose frame was already about right, are unchanged. Closes #181.
- **Fieldglass reads three more GRIB1 grid layouts.** Rotated/oblique lat/lon grids (`grid_type 10`, used by COSMO and other limited-area models) now parse their tilted pole and reproject like the GRIB2 rotated grids. Reduced — "quasi-regular" — lat/lon and Gaussian grids, which store fewer points toward the poles (the common ECMWF reduced-Gaussian layout), now decode their full field and render. And messages that carry no grid section at all now resolve the common predefined global grids (ON388 Table B grids 2, 3, and 4) by their catalogue number. Closes #47.
- **The globe-style projections can be recentred on any point.** The orthographic and polar-stereographic targets previously used a fixed set of centre and hemisphere presets. The render panel now takes free-form numbers: orthographic recentres on any centre longitude and latitude, and polar stereographic takes either pole with an arbitrary central meridian. Closes #113.

- **Real, attribute-heavy NetCDF-4 / HDF5 files now open.** Operational files such as NOAA GOES imagery carry enough metadata that their attributes spill out of HDF5's compact storage into a fractal heap with an *indirect* root block — a doubling table of storage blocks. Fieldglass previously stopped at the single-block case and refused these files; it now walks the doubling table, so their dimensions, variables, and attributes load like any other. Exercised by a real GOES-16 ABI file bundled in the test corpus. Part of #123.
- **Files with even more metadata now open.** When an HDF5 object has hundreds of attributes (or a group hundreds of links), the index over them is a multi-level B-tree — an internal-node tree rather than the single block smaller files use. Fieldglass previously walked only the single-level case and refused the rest; it now descends the internal nodes, so the dimensions, variables, and attributes of these larger files load too. This is the index-side counterpart to the doubling-table storage support above, and the gap a metadata-heavy operational file hits first. Exercised by a bundled fixture whose attribute index is two levels deep, cross-checked against libhdf5. Part of #33 / #123.
- **The most metadata-heavy NetCDF-4 / HDF5 files now open.** Once a file's attributes (or a group's links) overflow even the first tier of a fractal heap's storage blocks, the heap nests a second tier — *child indirect blocks* in its doubling table. Fieldglass walked only the first tier and refused the rest; it now recurses through the nested blocks, so the dimensions, variables, and attributes of these files load too. This is the storage-side counterpart to the multi-level index support above, and the next structure the metadata-heaviest operational files (MERRA-2, ERA5, CMIP6) reach. Exercised by a bundled fixture whose attribute heap nests one level deep, cross-checked against libhdf5. Part of #33 / #123.
- **Compressed (I/O-filtered) HDF5 metadata heaps now decode.** The fractal heap that holds an object's dense attributes (or a group's dense links) may have its storage blocks run through a compression filter. Fieldglass previously stopped at unfiltered heaps and refused a filtered one; it now reverses the heap's filter pipeline — deflate and shuffle, the same filters it already applies to dataset chunks — before reading the blocks, so a conforming file that uses one loads its dimensions, variables, and attributes like any other. Both the single-block and doubling-table heap layouts are covered. Part of #33.

### Fixed

- **GRIB1 second-order fields that are entirely constant now decode.** When every group in a second-order message has zero width, the file holds no second-order values and the pointer to them lands just past the end of the section. Fieldglass treated that as malformed and refused the message; it now decodes, matching eccodes. Closes #91.
- **Malformed GRIB1 files can no longer crash the reader.** A message that declared a length shorter than its own header, or that ended partway through a section's length field, used to panic instead of reporting a parse error. Both cases now surface a clean error. The crashes were found by a new fuzz target that exercises the GRIB1 decode path against arbitrary bytes, run as a time-boxed CI job. Closes #92.
- **Malformed GRIB2 files can no longer crash the reader.** Several crafted inputs used to crash instead of reporting a parse error: a message whose declared total length overflowed a 64-bit offset, one whose bit-map or data section declared a length running past the end of the message, and one whose grid dimensions disagreed with the grid's own declared point count (which could make decoding try to allocate gigabytes for a file that held no such data). All of these now surface a clean error. The crashes were found by a new fuzz target that exercises the GRIB2 decode path against arbitrary bytes, run as a time-boxed CI job. Closes #132.
- **Truncated GRIB1 matrix-of-values fields now report an error instead of mis-decoding.** When a matrix message's packed data ran short of what its secondary bitmap declared, the decoder filled the gap with missing values and shifted every later value by one. It now surfaces a clean parse error, matching how the other packings handle a short data section.
- **Hardened parsing of untrusted files.** A NetCDF header name length is now bounded by a fixed cap rather than the file size, a GRIB2 end-of-message check guards its own bounds locally, and the projection code sorts with a total order so a stray non-finite value can't panic a render. None of these change how valid files decode.
- **Small NetCDF attribute values now show in full.** The metadata viewer rounded numeric attributes to six decimal places, so a tiny value like a GOES `scale_factor` of about 0.00000067 displayed as `0.000001`. Numeric attributes now show their exact stored value. Closes #184.
- **NetCDF fields that mark gaps with `missing_value` now mask them.** Decode masked only points equal to a variable's `_FillValue`; it now also masks the CF `missing_value` attribute, the older convention many products still use, so those gaps read as missing instead of as a real data spike. Both the classic and NetCDF-4 / HDF5 backings handle it, cross-checked against the netCDF4 library.
- **Global grids that start at the antimeridian now reproject correctly.** A regular lat/lon grid whose longitudes run eastward from 180° — the layout ECMWF open data uses — rendered mirrored in the equirectangular view and collapsed to a thin sliver at the seam in the orthographic and polar-stereographic views. Its longitude span was measured as a single grid step instead of the full globe. The reprojection now unwraps a grid that crosses the antimeridian, so it renders like a 0°-origin grid. The same fix covers Mercator and Gaussian source grids. Two related hardenings ride along: the rare grid that scans east-to-west now stays in its own coordinates instead of reprojecting wrongly, and a file with a corrupt (non-finite) grid corner now reports a clear error instead of rendering misplaced data.
- **Global grids no longer show a hairline gap at their wrap meridian.** A global grid stores each longitude once, so the last fraction of a degree between its final column and the first belongs to neither — the orthographic and polar-stereographic views drew it as a one-pixel seam line. The renderer now recognises a grid that spans the full globe and samples across the wrap, interpolating between the last and first columns, so the seam is continuous in every projection.
- **ECCC rotated grids no longer render split across the map.** The HRDPS continental grid's columns cross the antimeridian of its rotated frame, and the map window computed for it swept the wrong way around the globe — a nearly global window with the field split between its left and right edges. The window now follows the grid's true span, so the domain frames correctly in the equirectangular and Web Mercator views.
- **The render tab keeps its settings when you switch tabs.** Switching to another editor tab and back rebuilt the render panel with default selections — projection, centre, resampling, color range, bounds, overlays, and the NetCDF variable and slice pickers all reset. The panel now remembers its selections and restores them when its tab is shown again, repainting the image the way you left it.

- **Lambert grids with a 0–360 reference longitude no longer render blank.** A longitude wrap-around error projected every point off the grid when a file stored its `LoV` in the 0–360 range, as NCEP and Eta files do. These grids now reproject correctly.

Automatic bounds also follow the curved grid edges instead of just the corners (so northern data is no longer clipped), handle grids that cross the dateline or span more than half the globe, and frame them tightly.

- **Coastlines and the grid render cleanly at view edges.** A longitude wrap error used to split overlay lines at the edge of a regional or manually-windowed view, leaving a notch. Long lines whose endpoints both fall off-screen but whose path crosses it are now drawn, and the dateline split now applies only to views that actually wrap.

- **A Web Mercator window outside the valid band is rejected.** Web Mercator is only valid to about ±85° latitude. A window entirely outside that band used to collapse every row to one latitude; it is now rejected.

  general-extended, boustrophedonic, two-orders-of-SPD, plus-one-in-SPD)
  plus a derived `order_of_spd()` and `packing_type_label()` that mirrors
  eccodes' `packingType` (`grid_second_order`, `grid_second_order_SPD3`,
  `grid_second_order_row_by_row`, etc.).
- **GRIB1 `grid_second_order` decoder** for the general-extended family
  (`secondOrderOfDifferentWidth=1`, `secondaryBitmapPresent=0`,
  `generalExtended2ordr=1`). Lives at
  `crates/fieldglass-grib1/src/packing/second_order.rs` and handles
  `orderOfSPD ∈ 0..=3` plus boustrophedonic row-scan reordering. The
  control flow mirrors `DataG1SecondOrderGeneralExtendedPacking::unpack`
  in eccodes' source, with the byte-aligned section sizing rule from
  `Spd::compute_byte_count` / `UnsignedBits::compute_byte_count`. Pinned
  end-to-end against a `grib_get_data` snapshot of an ECMWF MARS-derived
  fixture: 29,040 grid points, every anchored sample matches eccodes to
  within 1e-3.
- **GRIB1 packing-mode compatibility table** in the README, distinguishing
  metadata coverage (every variant) from decode/render coverage (simple
  packing only today).
- **ECMWF GRIB1 test fixture** at
  `crates/fieldglass-grib1/tests/fixtures/ecmwf_lfpw_msg0.grib1` (56 KB,
  one message, `grid_second_order` SPD-2). Used by
  `tests/decode_ecmwf_complex.rs` to pin the variant-detection wiring;
  will become the oracle for the second-order decoder in a follow-up.
- **GRIB2 Indicator Section parsing** — `fieldglass-grib2` now parses Section 0 (16 bytes), enumerating messages by walking 64-bit total-length offsets and surfacing edition, discipline (WMO Code Table 0.0 lookup), and total length. New `open_grib2` napi function dispatches `.grb2` / `.grib2` files to the tabular viewer instead of the previous "no messages found" fallback. Sections 1–7 remain follow-ups.

### Changed

- Render is performed in *grid coordinates* — no map reprojection is applied,
  so polar stereographic and Lambert conformal grids show the data in scan
  order. Geographic reprojection is tracked as a separate follow-up.

### Fixed

- **GRIB1 PDS decimal scale factor `D` decoded as sign-magnitude** (per WMO
  spec) instead of two's-complement. Octet 27 high bit is the sign, low 15
  bits are the magnitude — reading the pair as a plain `i16` turned small
  negatives like `D = -2` (wire `0x8002`) into `-32766`, which silently
  multiplied every decoded value by `10^32766` (→ `±inf`). Both shipped
  fixtures happen to use `D = 0`, so the bug was invisible until
  cross-checking real ECMWF surface fields against eccodes. End-to-end
  regression in `tests/decode_ecmwf_complex.rs` patches the fixture's
  PDS to `D = -2` and pins the result against
  `grib_set -s decimalScaleFactor=-2` (eccodes 2.34.1).
- README feature matrix: replaced GitHub-only `$\color{red}{\textsf{Not yet}}$` LaTeX color hack with `❌ Not yet` so the table renders correctly inside the VS Code Marketplace listing as well as on GitHub (#25).
- Codecov badge in the README showed `unknown` because the coverage workflow's tokenless upload was being rejected (`Token required - not valid tokenless upload`) and silently swallowed by `fail_ci_if_error: false`. Switched the upload to OIDC (`use_oidc: true` plus `id-token: write` permission), which is the recommended tokenless path on `codecov-action@v5` for trusted runs (#24).
- **NetCDF CDF-5 variable header: `dimid` now read as 8-byte `NON_NEG`** (the
  CDF-5 width) instead of 4-byte. The previous code unconditionally read
  4 bytes, then ran the rest of the parse 4 bytes off and tripped the
  `att_list` ABSENT-with-non-zero-count guard partway through the var list.
  Surfaced by the new ERSST CDF-5 fixture (real NOAA NCEI data re-encoded
  by the canonical Unidata `netCDF4` library); unit tests in
  `classic.rs` happened to use synthetic CDF-1 fixtures so missed it.

## [0.1.0] — 2026-05-09

First public release, on the Marketplace pre-release channel. Read-only metadata viewer for GRIB1; GRIB2 and NetCDF detection only.

### Added

- **GRIB1 metadata viewer** — IS, PDS, GDS section parsing, with WMO ON388 lookups for parameter, originating centre, and level type. Tabular webview shows one row per message.
- **GRIB1 grid descriptions** — Lat/Lon, Gaussian, Polar Stereographic, Lambert Conformal projections.
- **GRIB1 Binary Data Section decoder** (`Grib1Reader::decode_message_values`, exposed via napi `decode_grid`) — produces per-point values respecting the optional Bit Map Section. Not yet wired to a 2-D visualization.
- **Format detection** for GRIB1, GRIB2, NetCDF (classic + NetCDF-4 / HDF5) from magic bytes.
- **File associations** for `.grb`, `.grib`, `.grib1`, `.grb1`, `.grb2`, `.grib2`, `.nc`, `.nc4`, `.netcdf`, plus an option-priority "Fieldglass Viewer" for arbitrary files via *Reopen Editor With…*.
- **Hex/ASCII fallback view** for files whose contents don't match a recognized format.
- **Pre-commit framework** orchestrating `cargo fmt`, `cargo clippy`, `tsc`, file-hygiene polish, `shellcheck`, `actionlint`, `gitleaks` on commit; `cargo test`, `cargo deny check`, `npm audit`, `semgrep` on push.
- **CI security suite** — Semgrep SAST, CodeQL (JS/TS + Rust, `security-extended`), Dependabot across `cargo` / `npm` / `github-actions`. Semgrep + CodeQL are visibility-gated and self-activate on flipping the repo public.
- **Test fixtures** for GRIB1 (CMC wind), GRIB2 (eccodes reduced Gaussian), and NetCDF (Unidata classic + HDF5 samples).
- **`SECURITY.md`** with the private vulnerability reporting workflow and scope.
- **Per-platform Marketplace packaging** — release workflow now builds one `.vsix` per `(linux|win32|darwin)` × `(x64|arm64)` target so users only download the binary they need.
- **`workflow_dispatch` dry-run** for the release workflow — manual runs build + package the matrix without publishing, so cross-build regressions can be caught before tagging.
- Dual licensing under **MIT OR Apache-2.0**, including a Marketplace-friendly `extension/LICENSE.md` summary.

### Changed

- CI: dropped the redundant `Build native (linux-x64 smoke test)` job. The native binary is already built (and now explicitly verified) inside `Build extension`.
- CI: cache cargo builds with `Swatinem/rust-cache` and Node.js downloads via `actions/setup-node`'s built-in `cache: npm` to cut warm-cache CI time.
- CI: switched `npm install` to `npm ci` in workflows so dependency installs respect the lockfile.
- pre-commit: aligned the local Semgrep rule set with the CI workflow by adding `p/owasp-top-ten` and `p/github-actions`; added a root-level `npm audit` hook to cover `@napi-rs/cli`.
- Marketplace listing metadata: `bugs.url`, `preview: true` (Preview badge while pre-release), and a `Visualization` category for discoverability.
- Versioning: dropped the `-beta.1` semver pre-release suffix in favour of the VS Code pre-release convention. The Marketplace rejects semver pre-release tags; future betas will be `0.1.1`, `0.1.2`, … with stable jumping to `0.2.0`.

### Notable display fixes

- GRIB1 GDS lat/lon decode now correctly handles WMO sign-and-magnitude encoding (was previously two's-complement, producing bogus bounds like `-8298.608°` for a valid `-90°` south pole).
- Level rendering is unit-aware: pressure levels show as `200 hPa`, height-above-ground as `2 m`, layer types as ranges (`100 – 85 kPa`), with `—` for fixed-surface types where the value byte has no meaning.
- Forecast time display respects the WMO time-range indicator: `+24h`, `0–24h accum`, `analysis`, etc., instead of collapsing to a raw P1 byte.
